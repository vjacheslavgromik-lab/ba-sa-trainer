**Цель главы.** Вы поймёте, что такое клиент и сервер, зачем нужен протокол и как выглядит обмен запросом и ответом в **HTTP** (Hypertext Transfer Protocol, «протокол передачи гипертекста»). Это основа для работы с любыми современными API.

## Почему общение по сети — особое

Программы внутри одного компьютера вызывают друг друга быстро и надёжно. По сети всё иначе. В книге «Шаблоны интеграции» названы четыре трудности (Введение):

- **Ненадёжность сети.** Данные идут через линии связи, маршрутизаторы и другие устройства, и на любом участке что-то может сломаться.
- **Низкая скорость.** Передача по сети на порядок медленнее обычного вызова внутри программы.
- **Различия между приложениями.** Разные языки, платформы, форматы данных.
- **Неизбежность изменений.** Приложения меняются, и интеграция должна это выдерживать.

Поэтому API, которым пользуются по сети, нужно проектировать иначе, чем обычные функции программы: заранее продумывать, что делать, если ответа нет или пришла ошибка.

## Клиент и сервер

В большинстве API общаются две стороны:

- **Клиент** отправляет запрос.
- **Сервер** принимает запрос и возвращает ответ.

HTTP определяет это так: клиент устанавливает соединение и отправляет запросы, сервер принимает соединения и отправляет ответы. Роли клиента и сервера привязаны к конкретному соединению (RFC 9110, §3.3). Один и тот же сервис может быть сервером для одних программ и клиентом для других.

## Что такое протокол

> **Определение.** Протокол — это договорённость о том, в каком порядке и в каком виде стороны обмениваются сообщениями.

Чтобы две программы понимали друг друга, они должны использовать один протокол. Самый распространённый протокол для API — **HTTP**. Он работает поверх надёжного соединения. В RFC 9110 сказано, что HTTP — это семейство протоколов типа «запрос — ответ», без сохранения состояния между запросами и на уровне приложения (§1.1, §3.3).

Что это значит на практике:

- **Запрос — ответ.** Клиент отправляет один запрос и получает ответ на него.
- **Без сохранения состояния.** Каждый запрос самодостаточен: сервер не обязан помнить предыдущий запрос. Всё нужное для обработки передаётся в самом запросе.
- **Прикладной уровень.** HTTP описывает смысл сообщений (что запрашивается, каков результат), а доставку байтов по сети выполняют протоколы ниже. Например, в Интернете данные передаются пакетами TCP/IP (Шаблоны интеграции, «Сообщение», с. 98). Это название двух протоколов: **TCP** (Transmission Control Protocol, «протокол управления передачей») и **IP** (Internet Protocol, «межсетевой протокол»).

## Ресурс и адрес

То, к чему обращается запрос, в HTTP называется **ресурсом**. Это может быть студент, курс, запись на курс: что угодно, чем управляет сервер. Ресурс обычно определяется адресом, который называется **URI** (Uniform Resource Identifier, «единый идентификатор ресурса»; RFC 9110, §3.1). Привычный вам **URL** (Uniform Resource Locator, «единый указатель ресурса») — это URI, который ещё и подсказывает, как ресурс найти (RFC 3986, §1.1.3).

Клиент получает не сам ресурс, а его **представление**: описание текущего состояния ресурса в передаваемом виде, например текст в формате **JSON** (JavaScript Object Notation, «запись объектов JavaScript») с данными студента (§3.2). О форматах представления мы поговорим в следующей главе.

## Как выглядит запрос и ответ

В HTTP клиент отправляет запрос с **методом** и **адресом ресурса**, а сервер отвечает **кодом состояния** (RFC 9110, §3.4). Рассмотрим пример для школы.

Запрос «покажи студента с номером 1»:

```
GET /students/1 HTTP/1.1
Host: school.example
Accept: application/json
```

Ответ сервера:

```
HTTP/1.1 200 OK
Content-Type: application/json

{"id": 1, "name": "Анна", "city": "Москва"}
```

Разберём по частям. В запросе:

- **метод** `GET` говорит, что нужно получить данные;
- **адрес** `/students/1` указывает ресурс — студента с номером 1;
- **заголовок** `Host` называет сервер, а `Accept` сообщает, в каком формате клиент хочет получить ответ (RFC 9110, §12.5.1).

В ответе:

- **код состояния** `200 OK` сообщает результат;
- **заголовок** `Content-Type` называет формат содержимого;
- **тело** — сами данные.

В RFC эти части называются управляющими данными (метод и адрес или код состояния), заголовками и содержимым (§6).

## HTTP и HTTPS

Если адрес начинается с `https`, обмен защищён. **HTTPS** — это тот же HTTP, но поверх соединения, защищённого шифрованием **TLS** (Transport Layer Security, «безопасность транспортного уровня»). Оно позволяет проверить, что вы говорите именно с нужным сервером, и скрывает передаваемые данные (RFC 9110, §4.2.2). Для API, которые передают персональные данные, используют HTTPS.
