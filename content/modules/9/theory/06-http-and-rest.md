**Цель главы.** Вы научитесь читать и проектировать REST API: выбирать ресурсы, называть их, подбирать метод HTTP и код ответа.

## Идея REST: API вокруг ресурсов

В SOAP операция названа внутри сообщения. В REST API строится иначе: сначала выделяют **ресурсы**, а действия выполняют **стандартные методы HTTP**.

> **Определение.** Ресурс — это объект, которым управляет API: студент, курс, запись на курс.

Такой подход называют ресурсо-ориентированным. Он описан в руководстве по проектированию API Google (AIP-121) и заимствует многие принципы REST. В нём ресурсы — это **существительные**, а действия над ними — **глаголы**, то есть методы. Поэтому вместо операции «получить студента» вызывают метод GET для ресурса «студент».

В HTTP это называется единообразным интерфейсом: все ресурсы доступны одним и тем же набором методов независимо от того, что это за ресурсы (RFC 9110, §1.1).

## Адрес ресурса

Адрес указывает на ресурс. Принята такая схема: **коллекция** (много однотипных ресурсов) и **идентификатор** конкретного ресурса:

- `/students` — все студенты (коллекция);
- `/students/1` — студент с номером 1;
- `/students/1/enrollments` — записи студента на курсы.

Правила имён (Google API Design Guide, AIP-122 «Resource names»):

- **Имя коллекции — существительное во множественном числе:** `students`, `courses`, `enrollments`. Если множественного числа нет, остаётся единственное: не нужно придумывать формы вроде `infos`.
- **Глаголов в пути нет.** `GET /students` понятнее и правильнее, чем `GET /getStudents`: действие уже задано методом GET.
- **Имя коллекции начинается со строчной буквы.** Руководство рекомендует `camelCase`, например `courseEnrollments`, и только латинские буквы и цифры.
- **Идентификатор ресурса** не содержит заглавных букв; дефисы допустимы: `les-miserables`.

Правила именования у разных команд различаются. В курсе важнее единообразие и отсутствие глаголов в пути.

## Методы HTTP

Метод говорит, какое действие нужно выполнить над ресурсом (RFC 9110, §9.3):

| Метод | Действие | Типичный успешный ответ |
|---|---|---|
| GET | получить ресурс | 200 |
| POST | создать новый ресурс или выполнить действие | 201 |
| PUT | создать или заменить ресурс | 200, 201 или 204 |
| DELETE | удалить ресурс | 204 |

Несколько уточнений.

**GET.** Тело запроса у GET не имеет определённой семантики, и отправлять его не следует (§9.3.1). Все данные для GET передаются в адресе.

**POST.** Сервер обрабатывает присланное тело. Если создан новый ресурс, сервер отвечает кодом 201 и в заголовке `Location` указывает его адрес (§9.3.3).

**PUT.** Создаёт ресурс или заменяет его присланным представлением. Ответ 201 означает «создан», 200 или 204 — «изменён» (§9.3.4).

**DELETE.** Просит удалить ресурс. Как и у GET, тело в запросе DELETE не имеет определённой семантики, отправлять его не следует (§9.3.5).

### Повторять запросы безопасно или нет

Метод **идемпотентен**, если несколько одинаковых запросов дают тот же результат, что и один (§9.2.2). Идемпотентны GET, PUT и DELETE. Повторное удаление уже удалённого студента ничего не изменит. А POST этого не гарантирует: два одинаковых POST могут создать две записи. Это важно, когда связь ненадёжна и клиент не знает, дошёл ли запрос.

## Коды состояния

Код в ответе показывает результат (RFC 9110, §15). Нужные нам:

| Код | Название | Когда |
|---|---|---|
| 200 | OK | запрос выполнен, в ответе данные |
| 201 | Created | создан новый ресурс (§15.3.2) |
| 204 | No Content | выполнено, содержимого в ответе нет, обычно после удаления (§15.3.5) |
| 400 | Bad Request | запрос неверный: ошибка синтаксиса, некорректное тело (§15.5.1) |
| 404 | Not Found | ресурс не найден (§15.5.5) |

Код 404 сообщает, что сервер не нашёл ресурс. Если известно, что ресурс удалён навсегда, лучше ответить 410 Gone (§15.5.5).

Коды **2xx** означают успех, **4xx** — ошибку клиента. Хороший API сообщает об ошибке понятным кодом, а не просто «что-то пошло не так».

## Формат тела и заголовки

Тело запроса и ответа передают в JSON (глава 3). Клиент сообщает формат тела заголовком `Content-Type: application/json` (§8.3) и может указать желаемый формат ответа заголовком `Accept` (§12.5.1).
