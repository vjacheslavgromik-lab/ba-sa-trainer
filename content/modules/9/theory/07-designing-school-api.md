**Цель главы.** Вы пройдёте весь путь от задачи до описания API на примере школы: выделите ресурсы, назовёте их, выберете методы и коды ответа, опишете тела запросов.

## Задача

В школе есть студенты и курсы, и студент может быть записан на несколько курсов. Данные уже знакомы по модулю 3: таблицы `students`, `courses` и `enrollments`. Приложению администратора нужен API, чтобы:

1. посмотреть список студентов и найти студента по номеру;
2. записать студента на курс;
3. отменить запись;
4. обновить данные студента.

## Шаг 1. Выделяем ресурсы

Ресурсы — это существительные из предметной области (глава 6). Берём их из таблиц базы:

- **студент** (`students`);
- **курс** (`courses`);
- **запись на курс** (`enrollments`), связь между студентом и курсом.

Запись на курс — тоже ресурс: у неё есть своя оценка, её можно создать и отменить.

## Шаг 2. Называем ресурсы и строим адреса

Коллекции получают имена во множественном числе, без глаголов (AIP-122):

- `/students` и `/students/{id}`;
- `/courses` и `/courses/{id}`;
- `/enrollments` и `/enrollments/{id}`.

Фигурные скобки `{id}` означают «здесь подставляется номер». На стадии проектирования их удобно использовать для обозначения идентификатора.

## Шаг 3. Подбираем методы

Для каждой задачи выбираем метод по смыслу действия (RFC 9110, §9.3):

| Задача | Метод и адрес |
|---|---|
| Список студентов | `GET /students` |
| Студент по номеру | `GET /students/{id}` |
| Записать студента на курс | `POST /enrollments` |
| Отменить запись | `DELETE /enrollments/{id}` |
| Обновить данные студента | `PUT /students/{id}` |

Обратите внимание: в адресах нет слов «получить», «записать», «удалить». Это делают методы.

## Шаг 4. Продумываем ответы

Для каждой операции выбираем код успешного ответа и коды ошибок (RFC 9110, §15):

| Операция | Успех | Ошибка |
|---|---|---|
| `GET /students` | 200 | |
| `GET /students/{id}` | 200 | 404, если студента нет |
| `POST /enrollments` | 201 | 400, если данные неверны |
| `DELETE /enrollments/{id}` | 204 | 404, если записи нет |
| `PUT /students/{id}` | 200 | 404, если студента нет |

Хороший API описывает **и успех, и ошибки**: потребителю одинаково важно знать, что вернётся в обоих случаях.

## Шаг 5. Описываем тела запросов

Операциям, которые что-то создают или меняют, нужно тело. Описываем его как JSON (глава 3).

`POST /enrollments`: запись студента на курс.

```json
{
  "student_id": 1,
  "course_id": 2
}
```

`PUT /students/{id}`: новые данные студента.

```json
{
  "name": "Анна",
  "city": "Казань"
}
```

Для каждого тела выписываем **обязательные поля** и их смысл: например, `student_id` — номер студента, `course_id` — номер курса. Заголовок запроса: `Content-Type: application/json`. У `GET` и `DELETE` тела нет.

## Шаг 6. Оформляем документацию

Таблица операций, описания тел и перечень ошибок — это только начало документации. Из них собирают **комплект документов**: таблицу операций, описание данных, каталог ошибок, примеры и спецификацию OpenAPI. По такому комплекту разработчик пишет код, а тестировщик собирает коллекцию в Postman. Как составить каждый документ, разберём в следующей главе.

## Типичные ошибки новичков

- **Глагол в адресе:** `POST /createEnrollment` вместо `POST /enrollments`.
- **Единственное число для коллекции:** `/student` вместо `/students`.
- **Тело у GET.** Данные для GET передают в адресе, а не в теле.
- **Только успех.** Нет описания, что вернётся, если студента нет или данные неверны.
- **Всегда 200.** Ошибка не должна выглядеть как успех: для неё есть свои коды.
