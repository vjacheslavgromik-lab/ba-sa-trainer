**Цель главы.** Вы познакомитесь с SOAP, одним из стилей API, научитесь читать SOAP-сообщение и документ **WSDL** (Web Services Description Language, «язык описания Web-служб»), которым описывают SOAP-службу. Это нужно, чтобы понять, чем отличается REST (глава 6).

## Что такое SOAP

**SOAP** — протокол обмена сообщениями в формате **XML** (Extensible Markup Language, «расширяемый язык разметки», глава 3). В ранних версиях спецификации название расшифровывалось как Simple Object Access Protocol, «простой протокол доступа к объектам»; в версии 1.2 это уже не аббревиатура (W3C, «SOAP Version 1.2 Part 1», раздел 1). Книга упоминает его как популярный стандарт удалённого взаимодействия, на котором строили Web-службы (с. 85). SOAP-сообщения обычно передают по HTTP (с. 98).

Идея SOAP такая: клиент отправляет серверу сообщение, в котором **указана операция и её данные**. Адрес один, а нужная операция называется внутри сообщения.

## Конверт

Сообщение SOAP версии 1.1 — XML-документ с корневым элементом **Envelope** («конверт»). Внутри конверта (с. 98):

- **Header** — необязательный заголовок: служебная информация;
- **Body** — обязательное тело: вызываемая операция и данные.

Пример запроса «получить студента с номером 1»:

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <m:GetStudent xmlns:m="https://school.example/students">
      <m:id>1</m:id>
    </m:GetStudent>
  </soap:Body>
</soap:Envelope>
```

Как читать: корневой элемент `Envelope` — это конверт; `Body` — его содержимое; `GetStudent` — **название операции**; `id` — её параметр.

## Команда и документ

В терминах обмена сообщениями SOAP-запрос можно рассматривать как **сообщение с командой**: оно просит выполнить операцию (с. 169). А если сообщение просто передаёт данные, это **сообщение с данными документа** (с. 171). Деление полезно при проектировании: понятно, отправляете ли вы «сделай» или «вот данные».

## Куда SOAP отправляет сообщение

По умолчанию SOAP-сообщение передаётся по HTTP, но книга отмечает, что его можно отправить и через систему обмена сообщениями (с. 98). Тогда сообщение SOAP окажется внутри сообщения системы доставки. Конверты, как матрёшки, вкладываются друг в друга.

## WSDL: как описывают SOAP-службу

Чтобы клиент мог вызвать SOAP-службу, он должен заранее знать: какие у неё есть операции, как выглядят запрос и ответ и куда их отправлять. Это записывают в отдельном документе, который называется WSDL. Если вспомнить главу 1, это **договор** между поставщиком и потребителем службы.

> **Определение.** **WSDL** (Web Services Description Language, «язык описания Web-служб») — формат на основе XML для описания сетевых служб как точек, которые принимают и отправляют сообщения (W3C, «Web Services Description Language (WSDL) 1.1»).

> **Примечание.** В русском издании книги «Шаблоны интеграции» название WSDL расшифровано как «язык определения Web-служб» (Definition). В стандарте W3C слово другое: Description, «описание».

В WSDL ничего не вызывают: этот документ только **описывает** службу. В книге сказано, что SOAP задаёт отдельные запрос и ответ для каждого вызова Web-службы, как определено в документе WSDL (Шаблоны интеграции, гл. 9, раздел «Синхронная реализация с использованием Web-служб»). А в разделе про каноническую модель данных отмечено, что WSDL задаёт структуру запросов и ответов, которые служба может принимать и выдавать (шаблон «Каноническая модель данных» начинается на с. 367, пример «WSDL»).

### Из чего состоит WSDL

В версии 1.1 служба описывается шестью основными элементами (W3C, WSDL 1.1, раздел 2.1 «WSDL Document Structure»):

- **types** — определения типов данных, из которых состоят сообщения;
- **message** — абстрактное описание передаваемых данных, составленное из частей;
- **portType** — набор абстрактных операций, у каждой есть входное и выходное сообщения;
- **binding** — конкретные протокол и формат данных для этих операций (например, SOAP по HTTP);
- **port** — адрес, по которому доступна привязка;
- **service** — группа связанных портов.

Первые три элемента отвечают на вопрос **«что делает служба»** и не зависят от протокола, последние три отвечают на вопрос **«как и куда обращаться»**. Такое разделение удобно: описание операций можно не менять, если служба переедет на другой адрес.

### Пример для API школы

Вот описание той же операции «получить студента», которую мы вызывали SOAP-запросом выше:

```xml
<definitions name="SchoolService"
    targetNamespace="https://school.example/students"
    xmlns="http://schemas.xmlsoap.org/wsdl/"
    xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
    xmlns:tns="https://school.example/students"
    xmlns:xsd="http://www.w3.org/2001/XMLSchema">

  <types>
    <xsd:schema targetNamespace="https://school.example/students"
        elementFormDefault="qualified">
      <xsd:element name="GetStudent">
        <xsd:complexType>
          <xsd:sequence>
            <xsd:element name="id" type="xsd:int"/>
          </xsd:sequence>
        </xsd:complexType>
      </xsd:element>
      <xsd:element name="GetStudentResponse">
        <xsd:complexType>
          <xsd:sequence>
            <xsd:element name="name" type="xsd:string"/>
          </xsd:sequence>
        </xsd:complexType>
      </xsd:element>
    </xsd:schema>
  </types>

  <message name="GetStudentIn">
    <part name="body" element="tns:GetStudent"/>
  </message>
  <message name="GetStudentOut">
    <part name="body" element="tns:GetStudentResponse"/>
  </message>

  <portType name="StudentPort">
    <operation name="GetStudent">
      <input message="tns:GetStudentIn"/>
      <output message="tns:GetStudentOut"/>
    </operation>
  </portType>

  <binding name="StudentBinding" type="tns:StudentPort">
    <soap:binding style="document"
        transport="http://schemas.xmlsoap.org/soap/http"/>
    <operation name="GetStudent">
      <soap:operation soapAction="https://school.example/students/GetStudent"/>
      <input><soap:body use="literal"/></input>
      <output><soap:body use="literal"/></output>
    </operation>
  </binding>

  <service name="StudentService">
    <port name="StudentPort" binding="tns:StudentBinding">
      <soap:address location="https://school.example/soap"/>
    </port>
  </service>
</definitions>
```

Как читать:

1. В `types` описаны два элемента: запрос `GetStudent` с номером `id` и ответ `GetStudentResponse` с именем `name`. Запрос совпадает с тем, что в SOAP-примере выше.
2. В `message` каждый из них оформлен как сообщение: входное `GetStudentIn` и выходное `GetStudentOut`.
3. В `portType` описана операция `GetStudent`: на входе одно сообщение, на выходе другое.
4. В `binding` операция привязана к SOAP по HTTP.
5. В `service` и `port` указан адрес, куда отправлять запрос.

### Два стиля привязки: rpc и document

В привязке к SOAP у атрибута `style` бывает два значения: `rpc` и `document` (Шаблоны интеграции, гл. 9, подраздел «Стиль привязки»). Они связаны с шаблонами, о которых шла речь выше:

- **`rpc`** — SOAP-запрос в стиле удалённого вызова процедуры. В теле стоят имя вызываемого метода и значения его параметров. Такое сообщение — сообщение с командой (Шаблоны интеграции, «Сообщение с командой», с. 169, пример «SOAP и WSDL»).
- **`document`** — в теле передаётся документ XML, который просто переходит от отправителя к получателю. Это сообщение с данными документа (там же, «Сообщение с данными документа», с. 171, пример «SOAP и WSDL»).

В нашем примере выбран `document`.

### WSDL 2.0

Есть и вторая версия, WSDL 2.0 (W3C Recommendation, 2007). В ней другие названия: операции группирует **interface**, привязку к протоколу описывает **binding**, адрес с привязкой задаёт **endpoint**, а набор конечных точек с общим интерфейсом называется **service** (W3C, «WSDL Version 2.0 Part 1: Core Language», раздел 1.1). По смыслу `portType` из версии 1.1 соответствует interface, а `port` — endpoint. Основная идея не меняется: сначала описывается, что умеет служба, затем как к ней обратиться.

## Что дальше

Главное в SOAP:

1. Формат запроса — XML-конверт.
2. Операция названа **внутри** сообщения.
3. Транспорт обычно HTTP, но может быть и другой.
4. Службу описывают документом WSDL: операции, формат запроса и ответа, привязка к протоколу и адрес.

В следующей главе вы увидите противоположный подход: в REST операция определяется методом HTTP и адресом, а тело чаще всего пишут в JSON.
