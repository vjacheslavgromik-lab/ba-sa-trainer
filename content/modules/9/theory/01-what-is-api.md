## Пример из жизни: меню в ресторане

Когда вы заказываете блюдо в ресторане, вы не заходите на кухню и не выбираете продукты сами. Вы смотрите в меню, называете блюдо, и кухня готовит его. Вам не важно, какая там плита и кто повар. Важно знать, **что можно заказать**, **как это назвать** и **что вы получите**.

Меню — это интерфейс между вами и кухней. Кухня может поменять плиту или повара, а меню останется тем же, и вам ничего не придётся менять в своём заказе.

С программами всё устроено так же. Одна программа хочет получить данные или возможности другой. Она не лезет внутрь чужой программы, а обращается через заранее оговорённые операции.

## Что такое программный интерфейс

> **Определение (рабочее определение курса).** Программный интерфейс, или **API** (Application Programming Interface, «программный интерфейс приложения»), — это набор операций и правил, через которые одна программа обращается к данным и возможностям другой программы.

Здесь всегда есть две стороны:

- **поставщик** — программа, которая предоставляет операции (в ресторане это кухня);
- **потребитель** — программа, которая их вызывает (это вы с заказом).

Пример. У школы есть система учёта студентов и курсов. Приложению для администратора нужно записать студента на курс. Оно не читает таблицы школьной базы напрямую, а вызывает операцию «записать студента на курс» и передаёт ей номер студента и номер курса. Что внутри этой операции, приложению знать не нужно.

## Интерфейс скрывает устройство программы

В книге «Шаблоны интеграции корпоративных приложений» эта идея описана через **инкапсуляцию**. Каждое приложение можно представить как объект: данные спрятаны внутри, а наружу выставлен интерфейс. Если другому приложению нужны данные или действие, оно обращается через вызов функции. Тогда приложение само следит за целостностью своих данных и может менять их формат, не затрагивая остальные приложения (Шаблоны интеграции, «Удалённый вызов процедуры», с. 85).

Сравните с другим подходом: если все приложения читают одну и ту же базу напрямую, любое изменение таблицы может сломать каждое из них. Интерфейс защищает от этого: пока операции работают как раньше, внутри можно менять что угодно.

> **Запомните.** API — это граница между двумя программами. Снаружи видны только операции, внутри остаётся реализация.

## Программный и пользовательский интерфейс

Слово «интерфейс» вам знакомо по экранам приложений. Это другой вид интерфейса:

- **Пользовательский интерфейс** (экран, кнопки, формы) создан для **человека**.
- **Программный интерфейс** (API) создан для **другой программы**.

Один и тот же сервис часто имеет оба. Когда администратор нажимает кнопку «Записать», приложение за экраном вызывает операцию API школы.

## Из чего состоит описание API

Чтобы потребитель смог пользоваться API, поставщик должен ответить на несколько вопросов. Именно эти ответы и описывает системный аналитик:

1. **Что можно вызвать.** Какие есть операции, например «получить студента» или «записать на курс».
2. **Как обратиться.** Адрес и способ вызова.
3. **Что передать.** Какие данные нужны операции (например, номер студента и номер курса) и в каком формате.
4. **Что вернётся.** Какой ответ получит потребитель при успехе.
5. **Что будет при ошибке.** Какие бывают ошибки и как о них сообщается: студента нет, данные неверные.

Это похоже на договор между поставщиком и потребителем: стороны заранее договариваются, что и как вызывается, и обе придерживаются договорённости.

## Зачем компаниям API

Приложения в компании покупают у разных поставщиков и пишут в разное время на разных платформах. Но они должны работать вместе. В книге названы критерии, по которым выбирают способ их связать (Шаблоны интеграции, гл. 2):

- приложения должны как можно меньше зависеть друг от друга (**слабое связывание**);
- внутри одного приложения должно быть можно что-то менять, не ломая остальные;
- приложения не обязаны знать язык, платформу и внутреннее устройство друг друга.

Хорошо описанный API позволяет выполнить все три условия.

## Что делает системный аналитик

Аналитик не пишет код API, но участвует в его проектировании. Согласно программе курса, он помогает определить, какие операции нужны, как они называются, какие данные передают и какие ответы возвращают. Для этого он описывает API так, чтобы это было понятно и разработчикам, и тем, кто будет пользоваться интерфейсом.
