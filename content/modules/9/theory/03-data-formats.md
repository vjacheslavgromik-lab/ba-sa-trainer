**Цель главы.** Вы узнаете, как данные упаковываются для передачи, и научитесь читать и писать JSON, главный формат современных API.

## Данные нужно упаковать

Программа хранит данные в памяти: объекты, записи, строки таблицы. По сети их нельзя передать «как есть», потому что у другой программы своя память. Данные нужно превратить в текст или набор байтов, которые получатель сможет разобрать. Для передачи данные упаковывают в **сообщение** (Шаблоны интеграции, «Сообщение», с. 98).

В сообщении две части:

- **заголовок** — служебная информация для системы доставки: например, адреса отправителя и получателя;
- **тело** — сами данные.

Вы уже видели это в HTTP: в запросе есть заголовки (`Host`, `Accept`) и тело.

## Формат данных

Чтобы получатель смог прочитать тело, обе стороны должны **договориться о формате**: как записаны числа, строки, списки и вложенные объекты. Без такой договорённости данные превращаются в набор непонятных символов.

Если формат у отправителя и получателя разный, его преобразуют по дороге. В книге такой преобразователь называется транслятором сообщений (с. 115).

Два самых распространённых формата в API:

- **XML** (Extensible Markup Language, «расширяемый язык разметки») — данные размечены тегами. Книга называет его основой современных интеграционных решений (с. 80). В XML передаются сообщения **SOAP** (в ранних версиях — Simple Object Access Protocol, «простой протокол доступа к объектам»; подробнее в главе 5).
- **JSON** (JavaScript Object Notation, «запись объектов JavaScript») — компактный текстовый формат. Именно в нём чаще всего передают данные **REST** API (REST — Representational State Transfer, «передача состояния представления»; о нём глава 6).

## Один и тот же студент в двух форматах

Запись о студенте в XML:

```xml
<student>
  <id>1</id>
  <name>Анна</name>
  <city>Москва</city>
</student>
```

Та же запись в JSON:

```json
{
  "id": 1,
  "name": "Анна",
  "city": "Москва"
}
```

Видно, что JSON короче: нет закрывающих тегов. Поэтому его проще читать и передавать.

## JSON подробно

> **Определение.** JSON — текстовый формат для записи структурированных данных (RFC 8259, §1).

Значение в JSON — это одно из следующих (§3):

| Тип | Как записывается | Пример |
|---|---|---|
| Объект | пары «имя: значение» в фигурных скобках (§4) | `{"id": 1, "name": "Анна"}` |
| Массив | список значений в квадратных скобках (§5) | `[1, 2, 3]` |
| Число | десятичное число, возможна дробная часть (§6) | `15000`, `4.5` |
| Строка | текст в двойных кавычках (§7) | `"Москва"` |
| Логическое | `true` или `false` строчными буквами | `true` |
| Пусто | `null` | `null` |

Объекты и массивы можно вкладывать друг в друга. Например, студент с его записями на курсы:

```json
{
  "id": 1,
  "name": "Анна",
  "enrollments": [
    {"course_id": 1, "grade": 5},
    {"course_id": 2, "grade": 4}
  ]
}
```

## Правила, о которых забывают

- **Имена в объекте должны быть уникальными.** Если имя повторяется, разные программы поведут себя по-разному: одна возьмёт последнее значение, другая сообщит об ошибке (RFC 8259, §4).
- **Строки в двойных кавычках.** Одинарные кавычки в JSON недопустимы.
- **Запятая между элементами, но не после последнего.** Лишняя запятая делает JSON неверным.
- **Кодировка UTF-8** (формат преобразования символов Юникода в байты, RFC 3629). Если JSON передают между системами, которые не входят в одну закрытую среду, он должен быть в кодировке UTF-8 (§8.1). Русские буквы поэтому передаются без проблем.
- **Неверный JSON не разберётся.** Получатель вернёт ошибку, а не часть данных. Поэтому корректность тела проверяют заранее, в том числе в Postman (глава 9).

## Как сообщить формат: заголовок Content-Type

Заголовок `Content-Type` сообщает, в каком формате тело сообщения (RFC 9110, §8.3). Для JSON значение такое: `application/json` (оно зарегистрировано в RFC 8259, §11). Если тело есть, а формат не указан, получатель не знает, как его читать.
