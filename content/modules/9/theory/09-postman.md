**Цель главы.** Вы научитесь собирать коллекцию запросов в Postman, использовать переменные и проверять коды ответа. Тренажёр этого модуля проверяет именно такие коллекции.

## Что такое Postman и зачем он аналитику

Postman — программа, в которой можно отправлять запросы к API и смотреть ответы, не написав ни строчки кода. Аналитик использует её, чтобы проверить, что описанный API работает так, как задумано.

Запросы в Postman хранятся в **коллекции**: файле, в котором запросы собраны в **папки** по назначению. Например, папка «Студенты» и папка «Записи» (Postman Learning Center, «Manage and organize Postman Collections»).

## Запрос в коллекции

У запроса есть:

- **название** по смыслу, например «Студент по номеру», а не «New Request»;
- **метод** и **адрес**;
- **заголовки**, например `Content-Type`;
- **тело**, если оно нужно;
- **тесты**: проверки ответа.

## Переменные: хост не пишем в адрес

Адрес сервера лучше не вписывать в каждый запрос. Вместо этого его кладут в **переменную**, например `baseUrl`, и пишут в адресе `{{baseUrl}}/students`. Тогда, чтобы переключиться между тестовым и боевым серверами, достаточно поменять значение переменной в одном месте (Postman Learning Center, «Reuse data with variables and environments in Postman»).

```
GET {{baseUrl}}/students/1
```

Двойные фигурные скобки означают «подставить значение переменной».

## Тесты: проверяем код ответа

Запрос без проверки ничего не доказывает: он просто отправился. Чтобы Postman сообщал, правильно ли ответил сервер, в запрос добавляют тест. Самый важный тест проверяет код ответа (Postman Learning Center, «Postman test script examples»):

```javascript
pm.test("Код ответа 200", function () {
  pm.response.to.have.status(200);
});
```

Для запроса, который должен закончиться ошибкой, проверяют ожидаемый код ошибки:

```javascript
pm.test("Студента нет: 404", function () {
  pm.response.to.have.status(404);
});
```

Хорошая коллекция проверяет **и успех, и ошибки**: для `GET /students/{id}` два запроса. Один обращается к существующему студенту и ждёт 200, другой — к несуществующему и ждёт 404.

## Тело запроса

Для POST и PUT нужно тело. Его пишут как корректный JSON и указывают `Content-Type: application/json`. В Postman для этого в настройках тела выбирают тип raw и язык JSON.

```json
{"student_id": 1, "course_id": 2}
```

## Экспорт коллекции

Готовую коллекцию экспортируют в файл JSON в формате Collection v2.1. Этот файл вы загрузите в тренажёр.

## Что проверяет тренажёр

Тренажёр читает файл и проверяет структуру коллекции. Запросы к API он не отправляет. Ищет такие нарушения:

- **Метод и тело (P1).** У GET и DELETE тела нет, у POST и PUT оно есть.
- **Тело JSON (P2).** Тело корректно, указан `Content-Type: application/json`.
- **Хост (P3).** В адресе переменная `{{baseUrl}}`, а не жёстко записанный сервер; адрес не пустой.
- **Код ответа (P4).** У каждого запроса есть тест на код ответа.
- **Название (P5).** Запрос назван по смыслу.
- **Имена ресурсов (P6).** Существительные во множественном числе, без глаголов, с первой строчной буквой.
- **Правила задания.** Какие запросы обязательны, какие коды ответа должны проверяться и какие поля нужны в теле. Они берутся из условия кейса.

Тренажёр показывает список нарушений: номер, правило, запрос и подсказку со ссылкой на источник. Исправляйте коллекцию, загружайте снова, пока нарушений не станет 0.

## Чек-лист перед загрузкой

1. Запросы разложены по папкам и названы по смыслу.
2. Хост записан переменной `{{baseUrl}}`.
3. В путях только существительные во множественном числе.
4. У POST и PUT есть корректное JSON-тело и `Content-Type: application/json`; у GET и DELETE тела нет.
5. В каждом запросе есть тест на код ответа.
6. Для операций с поиском по номеру есть запрос с ошибкой (404).
7. Каждой операции из спецификации API (глава 8) соответствует запрос в коллекции.
