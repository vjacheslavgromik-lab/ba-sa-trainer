**Цель главы.** Вы научитесь показывать, как участники общаются друг с другом по шагам, на диаграмме последовательности. Таблица операций (глава 7) описывает отдельные вызовы, а диаграмма показывает весь сценарий от начала до конца.

В этой главе описана базовая нотация по книге Вендрова. Синхронные и асинхронные сообщения, полосы активации и условные ветви в источнике не рассматриваются, поэтому здесь их нет.

## Зачем нужна диаграмма

Таблица API показывает отдельные операции. Но когда пользователь нажимает «Записать студента», происходит цепочка вызовов между приложением, API и базой. Диаграмма последовательности показывает эту цепочку **во времени**.

## Диаграммы взаимодействия

Диаграммы взаимодействия описывают, как группа объектов взаимодействует в рамках варианта использования или операции (Вендров, п. 2.5.2). Обычно диаграмма охватывает один поток событий: один сценарий.

**Сообщение** — способ, которым отправитель просит получателя выполнить одну из его операций. Вендров выделяет три вида:

- **информационное** сообщает получателю данные для обновления его состояния;
- **запрос** просит выдать информацию о получателе;
- **императивное** просит выполнить действие.

Есть два вида таких диаграмм: **диаграмма последовательности** (упорядочена по времени) и **кооперативная** (акцент на связях между объектами).

## Как читать диаграмму последовательности

Она показывает **временную последовательность событий** в рамках сценария (п. 2.5.2).

- В **верхней части** стоят действующие лица и объекты, нужные для выполнения сценария.
- Каждый объект изображается прямоугольником на вершине пунктирной вертикальной линии. Эта линия — **линия жизни**: она показывает отрезок жизни объекта во время взаимодействия.
- **Сообщение** — стрелка между линиями жизни двух участников.
- Сообщения идут **сверху вниз** в том порядке, в каком происходят. У каждого есть хотя бы имя; можно добавить аргументы.
- **Самоделегирование** — сообщение, которое участник посылает самому себе: стрелка начинается и заканчивается на его линии жизни.

Вендров показывает это на примере «Снять деньги со счёта»: клиент вставляет карту, вводит PIN-код и сумму, система проверяет средства и выдаёт деньги. Сообщения на диаграмме пронумерованы по порядку.

## Как найти участников

Один из способов — выписать **существительные из описания сценария** (п. 2.5.2). Но на диаграмме бывают объекты, о которых в тексте не сказано:

- **формы** для ввода и просмотра данных, чтобы действующее лицо могло вводить информацию в систему или видеть её;
- **управляющие объекты**, которые управляют последовательностью событий.

## Кооперативная диаграмма

Вторая разновидность показывает тот же сценарий, но подчёркивает **связи между участниками**, а не время. Порядок задаётся **номерами** сообщений. По диаграмме последовательности легче понять порядок, по кооперативной — связи, поэтому часто создают обе (п. 2.5.2).

## Пример: записать студента на курс

Сценарий: администратор записывает студента на курс через приложение, которое вызывает API школы.

**Участники слева направо:**

1. Администратор (действующее лицо)
2. Приложение (клиент API)
3. API школы
4. База данных

**Сообщения сверху вниз:**

1. Администратор → Приложение: выбрать студента и курс.
2. Приложение → API школы: `POST /enrollments` с телом `{"student_id": 1, "course_id": 2}`.
3. API школы → База данных: проверить, что студент и курс существуют.
4. API школы → База данных: сохранить запись.
5. API школы → Приложение: ответ `201 Created`.
6. Приложение → Администратор: показать «Студент записан».

Заметьте: шаг 2 — это та самая операция из главы 7, а шаг 5 — её ответ. Если студента или курса нет, на шаге 5 вместо 201 придёт код ошибки, например 404 или 400. Это другой поток событий, и для него рисуют отдельную диаграмму.

**Как проверить диаграмму:**

- все участники из сценария присутствуют;
- у каждого сообщения есть имя;
- порядок сообщений совпадает с порядком шагов;
- ответ API показан отдельным сообщением.
