**Цель главы.** Вы узнаете, какие документы (артефакты) создаёт аналитик при проектировании API, научитесь составлять спецификацию API в стандарте OpenAPI и проверять комплект документации на полноту.

## Зачем документировать API

В главе 1 мы сравнили API с договором между поставщиком и потребителем. Договор нужно **записать**: иначе каждый участник понимает его по-своему. Разработчик пишет код, тестировщик проверяет ответы, другая команда подключает своё приложение, и всем нужен один и тот же источник правды.

Хорошая документация позволяет и человеку, и программе понять возможности сервиса, не заглядывая в исходный код (OpenAPI Specification, раздел «Introduction»). Описание API — один из главных результатов работы аналитика.

## Какие артефакты нужны

> **Определение.** **Артефакт документирования** — документ или модель, которые создаются в проекте и по которым работают другие участники. Спецификация API — один из таких артефактов.

Для API школы мы составим такой набор:

| Артефакт | Что показывает | Для кого |
|---|---|---|
| Таблица операций | метод, адрес, назначение, ответы | все участники |
| Описание данных | поля тел запросов и ответов | разработчики, тестировщики |
| Каталог ошибок | коды ошибок и когда они возникают | разработчики, потребители API |
| Примеры запросов и ответов | как выглядит реальный обмен | потребители API |
| **Спецификация OpenAPI** | всё перечисленное в одном файле, понятном и человеку, и программе | все участники и инструменты |
| Диаграмма последовательности | как участники общаются в сценарии (глава 10) | аналитики, разработчики |
| Диаграмма компонентов | из каких частей состоит система и как они связаны | разработчики, архитекторы |
| Коллекция Postman | проверка, что API работает как описано (глава 9) | тестировщики, аналитики |

Похожий набор указан в программе курса: в проекте по API нужно составить диаграмму компонентов, смоделировать профиль API и собрать коллекцию запросов в Postman. Теперь рассмотрим каждый артефакт.

## Таблица операций

Вы составили её в главе 7: каждой операции соответствуют метод и адрес, назначение и коды ответа. Это краткий обзор API для всех участников проекта.

## Описание данных

Для каждого тела запроса и ответа опишите поля. Описывайте не только названия, но и смысл, и ограничения.

Пример для `POST /enrollments` (запись студента на курс):

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `student_id` | целое число | да | Номер студента из таблицы `students` |
| `course_id` | целое число | да | Номер курса из таблицы `courses` |

Если поле может быть пустым, это нужно указать явно. Например, у студента город может быть не задан (`NULL` в базе, как в модуле 3), и в JSON это значение `null`.

## Каталог ошибок

Потребитель должен знать заранее, что значит каждая ошибка и что с ней делать (коды состояния определены в RFC 9110, §15).

| Код | Когда возникает | Что делать клиенту |
|---|---|---|
| 400 | в теле нет `course_id` или значение не число | исправить запрос |
| 404 | студента с таким номером нет | проверить номер |

## Примеры запросов и ответов

Один реальный пример часто понятнее длинного описания.

Запрос:

```
POST /enrollments
Content-Type: application/json

{"student_id": 1, "course_id": 2}
```

Ответ при успехе: `201 Created`. Ответ при ошибке (нет поля `course_id`): `400 Bad Request`.

## Спецификация OpenAPI

Таблицы удобны для чтения, но программа их не поймёт. Для этого есть стандарт **OpenAPI Specification** (OAS), который публикует организация OpenAPI Initiative. Он определяет стандартный, не привязанный к языку программирования способ описать HTTP API так, чтобы описание понимали и люди, и программы (OpenAPI Specification v3.1.1, «Introduction»).

Спецификация — это один документ в формате **YAML** (текстовый формат записи структур, удобный для чтения человеком) или JSON (§3.2 «OpenAPI Document», §4.2 «Format»). Если вы читали JSON в главе 3, структура вам знакома: те же объекты и массивы.

Вот спецификация для двух операций API школы:

```yaml
openapi: 3.1.1
info:
  title: API школы
  version: 1.0.0
paths:
  /students/{id}:
    get:
      summary: Получить студента по номеру
      parameters:
        - name: id
          in: path
          required: true
          description: Номер студента
          schema:
            type: integer
      responses:
        "200":
          description: Студент найден
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Student"
        "404":
          description: Студента с таким номером нет
  /enrollments:
    post:
      summary: Записать студента на курс
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/EnrollmentRequest"
            example:
              student_id: 1
              course_id: 2
      responses:
        "201":
          description: Запись создана
        "400":
          description: Данные неверны
components:
  schemas:
    Student:
      type: object
      required: [id, name]
      properties:
        id:
          type: integer
        name:
          type: string
        city:
          type: [string, "null"]
          description: Город; пусто, если не указан
    EnrollmentRequest:
      type: object
      required: [student_id, course_id]
      properties:
        student_id:
          type: integer
        course_id:
          type: integer
```

### Как читать спецификацию

Разберём по частям.

- **`openapi`** — версия стандарта, по которому написан документ. Обязательное поле.
- **`info`** — сведения о документе: `title` (название) и `version` (версия). Оба поля обязательны. Версия здесь относится к самому документу, а не к API и не к стандарту (§4.8.2).
- **`paths`** — адреса и операции. Ключ начинается с косой черты. Фигурные скобки в `/students/{id}` — **шаблон пути**: на их место подставляется значение (§3.5).
- **Операция** (`get`, `post`) описывает действие: краткое назначение (`summary`), параметры, тело запроса и ответы.
- **Параметр пути.** Для него `in: path`, имя должно совпадать с именем в шаблоне (`id`), а `required` должно быть `true` (§4.8.12).
- **`responses`** — коды ответов. Должен быть хотя бы один. У каждого ответа обязательно описание (`description`) (§4.8.16, §4.8.17).
- **`components`** — повторно используемые описания. `Student` и `EnrollmentRequest` описаны один раз и подключаются через ссылку `$ref: "#/components/schemas/Student"` (§4.8.7, §4.8.23). Если форму тела изменить в одном месте, она изменится везде.
- **Схема данных** (`schema`) описывает тип значения: объект, целое число, строка. В версии 3.1 схемы строятся на стандарте JSON Schema (черновик 2020-12). Поле `required` в схеме перечисляет обязательные свойства; запись `type: [string, "null"]` значит «строка или пусто».

Обратите внимание: все пять артефактов из таблицы выше здесь соединены в одном документе: операции, адреса, поля, ошибки и пример.

> **Запомните.** Спецификацию читают и люди, и программы. Поэтому она должна быть формально корректной: у каждого ответа есть описание, параметр пути обязательный, ссылки ведут на существующие схемы.

В этой главе использована версия 3.1.1. У стандарта есть и более новые версии, например 3.2; основные понятия те же.

### А что для SOAP: WSDL

OpenAPI описывает REST API. У SOAP-служб есть своя спецификация: документ WSDL (глава 5). Сравним их по смыслу (сравнение составлено для курса):

| Что описывается | WSDL 1.1 (SOAP) | OpenAPI 3.1 (REST) |
|---|---|---|
| Операции | `portType` и его операции | `paths` и операции по методам: `get`, `post` |
| Данные запросов и ответов | `types` и `message` (схема XML) | `components` и `schemas` (JSON Schema) |
| Как обратиться | `binding`, `port`, `service` | метод HTTP и путь операции |
| Формат документа | XML | YAML или JSON |

Идея одна: описать API формально, чтобы его могли читать и люди, и программы. Различается стиль: в WSDL операции и привязка к протоколу описаны отдельно, а в OpenAPI всё про одну операцию собрано в одном месте.

## Диаграмма последовательности

Показывает сценарий во времени: кто кому и в каком порядке посылает сообщения. Подробно разобрана в главе 10. Она дополняет спецификацию: спецификация описывает операции по отдельности, а диаграмма — их цепочку.

## Диаграмма компонентов

Диаграмма компонентов показывает, из каких частей состоит система и как они зависят друг от друга. Компоненты соединяются зависимостями: например, один компонент не может быть собран, пока не существует другой. В модели системы бывает несколько диаграмм компонентов, по числу подсистем (Вендров, п. 2.5.6). В нашем курсе её составляют для API, чтобы показать, какие компоненты предоставляют интерфейс и какие его используют: приложение администратора, API школы, база данных.

## Коллекция Postman

Коллекция в Postman (глава 9) — это **исполняемая** документация: она не только описывает запросы, но и проверяет, что API отвечает так, как записано в спецификации.

## Как проверить комплект документации

Перед передачей документов разработке проверьте:

1. **Полнота.** Для каждой операции описаны метод, адрес, параметры, тело, ответ при успехе и **все** ответы при ошибках.
2. **Согласованность.** Имена ресурсов, поля и коды совпадают во всех артефактах: таблице, спецификации, примерах и коллекции.
3. **Корректность.** Спецификация формально верна: версия и название указаны, у каждого ответа есть описание, параметры пути обязательны, ссылки ведут на существующие схемы.
4. **Понятность.** Есть примеры, смысл полей объяснён, ограничения указаны.
5. **Актуальность.** При изменении API обновлены все артефакты, а у документа поднят номер версии (`info.version`).

## Проверьте себя

- Какие артефакты документирования вы составите для API школы? Для кого каждый из них?
- Зачем нужна спецификация OpenAPI, если уже есть таблица операций?
- Что значит запись `{id}` в адресе и что должно быть описано для этого параметра?
- Что произойдёт, если изменить схему `Student` в разделе `components`?
- Что означает поле `version` в блоке `info`?
