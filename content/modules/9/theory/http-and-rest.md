## 1. Запрос и ответ

HTTP — это взаимодействие «запрос — ответ»: клиент отправляет запрос, сервер возвращает ответ. Запрос содержит метод, адрес ресурса, заголовки и, возможно, тело. Ответ содержит код состояния, заголовки и, возможно, тело. Тот же принцип в обмене сообщениями называется «Запрос-ответ» (Шаблоны интеграции, с. 177): инициатор отправляет запрос и получает ответ.

## 2. Методы HTTP

Метод задаёт действие над ресурсом (RFC 9110, §9.3):

| Метод | Что делает | Тело запроса |
|---|---|---|
| **GET** (§9.3.1) | получить ресурс | у GET содержимое запроса не имеет определённой семантики; отправлять его не следует (SHOULD NOT) |
| **POST** (§9.3.3) | обработать присланное представление; если создан ресурс, сервер отвечает 201 с заголовком Location | тело есть |
| **PUT** (§9.3.4) | создать или заменить ресурс присланным представлением; 201, если создан, 200 или 204, если изменён | тело есть |
| **DELETE** (§9.3.5) | запросить удаление ресурса (в терминах RFC: убрать связь адреса с его текущей функциональностью) | как у GET: содержимое не имеет определённой семантики, отправлять не следует |

Метод **идемпотентен**, если несколько одинаковых запросов дают тот же эффект, что один (§9.2.2). Идемпотентны PUT, DELETE и безопасные методы (например, GET). Для POST это не гарантируется.

## 3. Заголовок Content-Type и формат тела

Заголовок `Content-Type` сообщает формат тела и то, как его обрабатывать (§8.3). Для JSON значение — `application/json` (см. тему «Представление данных и SOAP»). Если тело есть, а формат не указан, получатель не знает, как его читать.

## 4. Коды состояния

Код состояния в ответе показывает результат (RFC 9110, §15). Основные коды курса:

| Код | Раздел RFC | Когда используется |
|---|---|---|
| **201 Created** | §15.3.2 | запрос выполнен, создан новый ресурс; его адрес указан в Location или совпадает с адресом запроса |
| **204 No Content** | §15.3.5 | запрос выполнен, содержимого в ответе нет (типично для удаления) |
| **400 Bad Request** | §15.5.1 | сервер не обрабатывает запрос из-за ошибки клиента: неверный синтаксис, некорректное тело |
| **404 Not Found** | §15.5.5 | сервер не нашёл ресурс; если известно, что удалён навсегда, лучше 410 Gone |

Хороший тест проверяет не только успешный ответ, но и ошибочный: например, что запрос несуществующего студента даёт 404.

## 5. Ресурсы и их имена

В ресурсо-ориентированном API ресурсы — это существительные, а действия выполняют стандартные методы HTTP (Google API Design Guide, AIP-121 «Resource-oriented design»). Поэтому адрес `GET /students` лучше, чем `GET /getStudents`: глагол уже содержится в методе.

Правила имён (AIP-122 «Resource names»):

- **Коллекция называется существительным во множественном числе:** `students`, `courses`, `enrollments`. Если множественного числа нет, остаётся единственное; выдумывать формы вроде `infos` не следует.
- **Идентификатор коллекции — в `camelCase`,** начинается со строчной буквы, содержит только латинские буквы и цифры: `courseEnrollments`.
- **Идентификатор конкретного ресурса** не должен содержать заглавных букв; дефисы допустимы: `les-miserables`.
- Имя ресурса строится по схеме «коллекция / идентификатор»: `students/123`, `students/123/enrollments`.

Правила именования у разных команд различаются, поэтому в курсе важнее единообразие и отсутствие глаголов в путях.

## 6. Коллекция Postman

Postman хранит запросы в коллекции; запросы группируют в папки по назначению (Postman Learning Center, «Manage and organize Postman Collections»). Файл коллекции экспортируют в формате JSON (Collection v2.1).

Что нужно для структурной проверки:

- **Переменные.** Хост лучше хранить в переменной окружения, например `{{baseUrl}}`, а не писать в адресе запроса (Postman Learning Center, «Reuse data with variables and environments»).
- **Тесты.** В тестовом скрипте запроса проверяют код ответа: `pm.test(...)` и `pm.response.to.have.status(200)` (Postman Learning Center, «Postman test script examples», раздел «Test for a status code»).
- **Тело запроса.** Для POST и PUT тело есть, это корректный JSON, указан `Content-Type: application/json`.

## 7. Пример: API школы

Предметная область — та же, что в модуле 3:

| Операция | Запрос | Успех | Ошибка |
|---|---|---|---|
| Список студентов | `GET /students` | 200 | |
| Студент по идентификатору | `GET /students/{id}` | 200 | 404 |
| Записать студента на курс | `POST /enrollments` | 201 | 400 |
| Отменить запись | `DELETE /enrollments/{id}` | 204 | 404 |
| Обновить студента | `PUT /students/{id}` | 200 | 404 |

Тело `POST /enrollments`: `{"student_id": 1, "course_id": 2}`.

## 8. Что проверяет тренажёр

Тренажёр проверяет только структуру коллекции, запросы к API не отправляются. Он ищет нарушения по правилам; каждое правило опирается на разделы выше:

- **P1.** Метод и тело согласованы: у GET и DELETE тела нет, у POST и PUT оно есть (раздел 2).
- **P2.** Тело — корректный JSON, указан `Content-Type: application/json` (раздел 3).
- **P3.** Хост задан переменной, адрес не пустой и без пробелов (раздел 6).
- **P4.** У запроса есть проверка кода ответа (разделы 4 и 6).
- **P5.** Запрос назван по смыслу, а не «New Request».
- **P6.** Имена ресурсов в пути — существительные во множественном числе, без глаголов, с учётом регистра (раздел 5).
- **Правила кейса:** обязательные запросы, коды ответа и поля тела из условия задания (разделы 4 и 7).

## Глоссарий

- **Ресурс:** объект, которым управляет API; в пути это существительное.
- **Идемпотентный метод:** метод, повторный вызов которого не меняет результат.
- **Код состояния:** трёхзначное число в ответе, показывающее результат.
- **Коллекция Postman:** файл с запросами, папками и тестами.
- **Переменная окружения:** именованное значение, например `{{baseUrl}}`.
