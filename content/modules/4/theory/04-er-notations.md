**Цель главы.** Вы узнаете, чем различаются основные способы рисовать ER-диаграммы, научитесь читать обозначения кратности в нотации «воронья лапка» и записывать диаграмму текстом для ER-тренажёра.

## Нотаций несколько

У ER-модели нет единой стандартной системы обозначений (Коннолли, Бегг, с. 26). В книгах по проектированию баз данных обычно встречаются две общепринятые, и обе поддерживаются современными **CASE**-средствами (Computer-Aided Software Engineering, программы для автоматизации проектирования):

- **Нотация Чена.** Сущности изображают **прямоугольниками**, связи — **ромбами**; прямоугольники и ромбы соединены линиями (с. 26).
- **Нотация «воронья лапка» (Crow's Foot).** Сущности тоже изображают прямоугольниками, а связи — просто **линиями** между ними. Связь «один ко многим» или «многие ко многим» показывает значок «воронья лапка» на одном или обоих концах линии (с. 26).

Третий способ — **UML**. Авторы книги используют его в основных главах: сущность — прямоугольник с именем и списком атрибутов, а кратность подписывается на концах связи как диапазон (`0..1`, `1..*`). Первичный ключ в такой нотации отмечают дескриптором `{PK}`, производный атрибут — косой чертой перед именем, многозначный — диапазоном в квадратных скобках (с. 398, 409, 420). Нотации Чена и «воронья лапка» подробно показаны в приложении Д (с. 1365–1367) в таблицах символов и на примере одной и той же диаграммы.

Это не вопрос «правильно или неправильно»: разные нотации выражают одну и ту же модель. Важно использовать **одну нотацию на проект** и объяснить её читателям.

| Нотация | Сущность | Связь | Кратность |
|---|---|---|---|
| Чена | прямоугольник | ромб между сущностями | подписи на линиях |
| «Воронья лапка» | прямоугольник | линия | значки на концах линии |
| UML | прямоугольник с атрибутами | линия с именем | диапазон на концах (`0..*`) |

## «Воронья лапка» в Mermaid

ER-тренажёр этого модуля принимает диаграммы в формате Mermaid `erDiagram`. Mermaid использует именно нотацию «воронья лапка» для значков на концах связи; «лапка» показывает, что экземпляров может быть много (документация Mermaid, раздел о связях).

Связь записывается так: `СУЩНОСТЬ-1 маркер--маркер СУЩНОСТЬ-2 : подпись`. Маркер на каждом конце состоит из двух символов: **внешний** показывает максимум, **внутренний** — минимум.

| Слева | Справа | Смысл |
|---|---|---|
| `\|o` | `o\|` | ноль или один |
| `\|\|` | `\|\|` | ровно один |
| `}o` | `o{` | ноль или больше |
| `}\|` | `\|{` | один или больше |

Например, `CUSTOMER ||--o{ ORDER : "делает"` читается так: у одного клиента может быть ноль или много заказов, а у каждого заказа ровно один клиент.

Линия `--` обозначает **идентифицирующую** связь: дочерняя сущность не может существовать без родительской. Линия `..` обозначает **неидентифицирующую** связь: обе сущности существуют независимо.

## Атрибуты в Mermaid

Атрибуты записываются в фигурных скобках после имени сущности парами «тип имя». После имени можно указать ключ: `PK` (первичный), `FK` (внешний), `UK` (уникальный); несколько ключей через запятую, например `PK, FK`. Комментарий записывается в двойных кавычках в конце строки. Если после типа поставить `?`, атрибут необязательный (например, `string? middleName`).

Имена сущностей могут содержать любые символы Юникода, а имена с пробелами берут в двойные кавычки. Принято писать названия сущностей существительными в единственном числе.

## Полный пример: магазин «Накарабине»

```text
erDiagram
  CUSTOMER ||--o{ ORDER : "делает"
  ORDER ||--|{ ORDER_ITEM : "состоит из"
  PRODUCT ||--o{ ORDER_ITEM : "входит в"
  CATEGORY ||--o{ PRODUCT : "объединяет"
  CUSTOMER {
    int id PK
    string name
    string email UK
  }
  ORDER {
    int id PK
    int customer_id FK
    date created_at
  }
  ORDER_ITEM {
    int order_id PK, FK
    int product_id PK, FK
    int quantity
  }
  PRODUCT {
    int id PK
    int category_id FK
    string title
    int price
  }
  CATEGORY {
    int id PK
    string title
  }
```

Как читать:

1. Клиент делает ноль или много заказов; у заказа один клиент.
2. Заказ состоит из одной и более позиций.
3. Товар входит в ноль или много позиций, а позиция относится к одному товару.
4. Категория объединяет ноль или много товаров; у товара одна категория.
5. «Позиция заказа» — промежуточная сущность между заказом и товаром. Её ключ составной: `order_id` и `product_id`.

Скопируйте этот текст в ER-тренажёр (модуль 4, вкладка «Тренажёры»): вы увидите график и замечания.
