**Цель главы.** Вы научитесь читать и рисовать диаграмму классов UML, поймёте, чем она отличается от ER-диаграммы, и увидите, как она связана с моделью данных.

## Класс и объект

> **Определение.** **Класс** — множество объектов, связанных общностью свойств, поведения, связей и семантики. Класс **инкапсулирует** (объединяет) данные (атрибуты) и поведение (операции) и служит шаблоном для создания объектов (Вендров, п. 2.4.2).

Структура и поведение схожих объектов определяют общий для них класс. Объект — это экземпляр класса. Например, класс «Товар» — шаблон, а «Палатка Trail-2» — объект этого класса.

На диаграмме UML класс изображается **прямоугольником из трёх частей**: в первой имя класса, во второй атрибуты, в третьей операции (п. 2.4.2).

```text
Товар
-----------------------
- артикул: String
- название: String
- цена: int
-----------------------
+ изменитьЦену(цена: int)
+ вПродаже(): boolean
```

## Атрибуты и видимость

Атрибуты спрятаны внутри класса от других классов. Поэтому для каждого атрибута указывают **видимость**: какие классы могут его читать и менять. Вендров выделяет три значения (п. 2.4.2): открытый (public), закрытый (private) и защищённый (protected). Для защищённого атрибута в UML используется знак `#`. В примере книги (рис. 2.38) открытые атрибуты помечены знаком `+`; закрытые в UML обычно помечают знаком `-`, как в примере выше. Например, защищённый атрибут «Адрес» класса «Сотрудник» могут читать и менять сам «Сотрудник» и его потомки, но не класс «Компания». Рекомендация автора: в общем случае атрибуты стоит делать закрытыми или защищёнными, чтобы их значения не менялись неожиданно для класса.

## Операции

**Операция** описывает действие, которое может выполнить объект: само по себе, инициируя действия других объектов или координируя их (п. 2.4.2). У операции три части: **имя, параметры и тип возвращаемого значения**. Запись в UML:

```text
ИмяОперации(аргумент1: тип, аргумент2: тип): тип_результата
```

## Связи между классами

Классы связываются **ассоциациями**: линиями, которые показывают, что объекты классов взаимодействуют (п. 2.5.3). Классы связаны, если они непосредственно обмениваются сообщениями: в примере Вендрова класс «Счёт» связан с классом «Экран банкомата», а «Считыватель карты» с «Выдачей наличных» не связан, потому что они напрямую не общаются.

У ассоциации на каждом конце записывают **кратность**: сколько объектов этого класса участвует в связи (п. 2.4.2). Вендров приводит такую таблицу обозначений:

| Запись | Значение |
|---|---|
| `*` | много |
| `0` | нуль |
| `1` | один |
| `0..*` | нуль или больше |
| `1..*` | один или больше |
| `0..1` | нуль или один |
| `1..1` | ровно один |

Вендров прямо отмечает: **кратность в объектной модели аналогична кратности и классу принадлежности в модели «сущность — связь»** (с точностью до расположения показателя на диаграмме). Это те же `1..1`, `0..*` и `1..*`, которые вы уже записывали в ER-модели (глава 3).

Другие виды связей (п. 2.4.2):

- **Агрегация** — связь «целое — часть», у которой бывает несколько видов: «обладает», «включает», «участник» — они различаются тем, зависит ли часть от целого по существованию и транзитивна ли связь. Строгая форма «целое — часть» показана в книге как **композиция** (рис. 2.41).
- **Обобщение (наследование)** — класс «потомок» наследует свойства «предка»: например, «Почасовой сотрудник» и «Сотрудник на окладе» наследуют от «Сотрудник».
- **Зависимость** — изменение в одном элементе может повлечь изменения в другом: один класс посылает сообщение другому, включает часть его данных или использует другой как параметр операции.

Для ассоциаций можно ограничить **направление навигации**: если связь работает только в одну сторону, на её конце ставится стрелка. А **ролевые имена** подписывают роль, которую играет класс в связи.

## Класс-ассоциация

Иногда у связи есть собственные свойства. Вендров показывает это на примере классов «Студент» и «Курс»: если добавить атрибут «оценка», непонятно, в какой класс его поместить. В «Студент» его пришлось бы вводить для каждого курса, в «Курс» — для каждого студента. Решение — **класс-ассоциация**: связь сама становится классом с атрибутами. Это аналог связи с атрибутами в ER-модели (п. 2.4.2).

Для «Накарабине»: у связи «Заказ — Товар» есть атрибут «количество». На диаграмме классов получится класс-ассоциация «Позиция заказа», в ER-модели из главы 4 это промежуточная сущность `ORDER_ITEM`. Одна и та же идея выражена двумя нотациями.

## Диаграмма классов и стереотипы

Диаграмма классов определяет **типы классов системы и статические связи между ними**. На ней изображаются атрибуты и операции классов и ограничения на связи (Вендров, п. 2.5.3). Для группировки классов служат **пакеты**, а **стереотипы** указывают роль класса: «Entity» (сущность), «Boundary» (граничный класс, экранная форма) и «Control» (управляющий) (п. 2.5.3). Пример: для сценария «Снять деньги со счёта» в книге выделены классы-сущности «Счёт» и «Считыватель карты» и граничные классы «Экран банкомата» и «Выдача наличных».

## Диаграмма классов и модель данных

| | ER-диаграмма | Диаграмма классов |
|---|---|---|
| Что описывает | данные: сущности, связи, атрибуты | классы с данными **и поведением** |
| Операции | нет | есть |
| Видимость атрибутов | нет | есть |
| Кратность | да | да (те же обозначения) |
| Кому нужна | проектировщику БД и аналитику | разработчику приложения |

Диаграмму классов аналитик использует, чтобы показать разработчикам, из каких классов состоит предметная область и как они связаны; ER-диаграмму — чтобы спроектировать хранение данных.
