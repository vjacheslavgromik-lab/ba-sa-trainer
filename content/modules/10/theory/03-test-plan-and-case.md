**Цель главы.** Вы научитесь составлять план тестирования и тест-кейсы по требованиям и проверять, что каждое требование покрыто тестом.

## План тестирования

> **План тестирования** (test plan) — документ, описывающий цели, ресурсы и процессы для конкретной тестовой сессии продукта. Он документирует стратегию проверки соответствия продукта спецификациям и требованиям (Wikipedia, Test plan; пересказ).

Для сложных систем бывает общий план и планы подсистем. Формат документа может быть таким же разным, как продукты и организации. В статье выделены три основных элемента плана:

- **покрытие тестами** — что проверяют;
- **методы тестирования** — как проверяют, включая критерии успеха и неудачи;
- **ответственность** — кто что делает, что собирают и как хранят результаты.

### Структура по IEEE 829-2008

Wikipedia приводит разделы плана по стандарту IEEE 829-2008 (Institute of Electrical and Electronics Engineers, Институт инженеров по электротехнике и электронике):

- идентификатор плана; введение;
- объекты тестирования; функции, которые будут проверяться; функции, которые не проверяются;
- подход; критерии успеха и неуспеха;
- критерии приостановки и возобновления;
- результаты тестирования; задачи; требования к среде;
- ответственность; потребность в персонале и обучении;
- график; риски и запасные планы;
- утверждения.

Для небольшого проекта многое можно сократить, но идентификатор, объекты, подход, критерии, среда, график и ответственность нужны почти всегда.

## Тест-кейс

> **Тест-кейс** (test case) — спецификация входных данных, условий выполнения, процедуры тестирования и ожидаемых результатов для одного теста, направленного на конкретную цель, например проверку требования (Wikipedia, Test case (software); пересказ).

Набор тест-кейсов делает тестирование методичным. Формальные кейсы можно повторять на новых версиях, то есть использовать для регрессионного тестирования.

### Поля тест-кейса

По статье, письменный тест-кейс может содержать:

- идентификатор;
- описание или краткую цель;
- предусловия;
- шаги теста;
- ожидаемый результат;
- фактический результат;
- признак «пройден или нет»;
- категорию, автора, признак автоматизации и примечания.

Для каждого требования обычно нужно минимум два кейса: **позитивный** (так и должно работать) и **негативный** (как система реагирует на неправильное). Связь кейса с требованием фиксируется матрицей трассируемости (следующая глава). Самое трудоёмкое — создавать кейсы и обновлять их при изменениях системы.

## Как получить тесты из требований

Вигерс предлагает такой образ мыслей: сама попытка придумать, как проверить требование, — ценный приём качества. Если проверить его нельзя, видны неясность, пропуск или допущение (с. 338). Тестировщики определяют способ проверки для каждого требования: тестирование, экспертиза, демонстрация или анализ (с. 337).

Стратегии тестирования по требованиям (с. 338) зависят от:

- **действий** — проверка каждого действия пользователя;
- **данных** — граничные значения и классы эквивалентности;
- **логики** — условия и комбинации;
- **событий** — реакция на события;
- **состояний** — переходы между состояниями.

Тестировщики с опытом добавляют кейсы по истории продукта, ожидаемым сценариям использования, общим свойствам качества и случайным ситуациям (с. 338). Когда спецификация записана естественным языком, кейсы пишут вручную; автоматически их можно получать только из формальной спецификации.

Уровни тоже важны: тестирование по требованиям нужно на каждом уровне, а не только на пользовательском. Каждый модуль должен соответствовать собственной спецификации, даже если пользователь его функцию не видит. Системное тестирование по пользовательским требованиям необходимо, но недостаточно (с. 338).

### Граничные значения и классы эквивалентности

Для требования «записаться можно на время не раньше текущего момента и не позже чем через 60 дней» нужны кейсы:

- класс «допустимые даты»: сегодня, через 30 дней;
- граница: сегодня (проходит), вчера (отказ), через 60 дней (проходит), через 61 день (отказ);
- негативные: пустая дата, дата в неверном формате.

## Пример для сети клиник «Вита»

**Фрагмент плана тестирования онлайн-записи:**

```text
Идентификатор плана: ТП-ЗАП-1
Объекты: сайт записи, сервер приложений, служба уведомлений
Проверяется: поиск окон, запись, отмена, напоминание
Не проверяется: оплата (отдельный план)
Подход: приёмочные сценарии Gherkin вручную; регрессия автоматически при каждой сборке
Критерий успеха: все приёмочные сценарии пройдены, нет открытых критичных ошибок
Критерий приостановки: сервер тестовой среды недоступен более 2 часов
Среда: тестовый сервер, тестовая база пациентов
Ответственность: тестировщик — выполнение; аналитик — разбор расхождений с требованиями
График: тестирование спринта 1 — последние 3 дня спринта
```

**Тест-кейс:**

```text
ID: ТК-ОТМ-03
Цель: проверить отказ в отмене менее чем за 2 часа до приёма (требование ТР-ОТМ-2)
Предусловие: у пациента есть запись на сегодня через 1 час
Шаги: 1) открыть «Мои записи»; 2) выбрать запись; 3) нажать «Отменить»
Ожидаемый результат: отмена не выполнена; показан телефон регистратуры
Тип: негативный
```

## Итоги

- План тестирования описывает покрытие, методы и ответственность; структура по IEEE 829-2008 даёт полный список разделов.
- Тест-кейс — вход, условия, шаги и ожидаемый результат для одной цели.
- Для каждого требования нужны хотя бы позитивный и негативный кейсы.
- Попытка придумать тест показывает неясности и пропуски в требовании.
