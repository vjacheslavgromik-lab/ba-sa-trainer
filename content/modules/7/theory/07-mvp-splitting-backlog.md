**Цель главы.** Вы поймёте, что такое MVP и чем он не является, освоите пять приёмов разбиения крупных историй и научитесь проверять качество бэклога по четырём признакам DEEP (Detailed appropriately, Estimated, Emergent, Prioritised).

## MVP: минимальный жизнеспособный продукт

> **Определение.** **MVP** (Minimum Viable Product) — такая версия нового продукта, которая позволяет команде собрать максимум проверенных знаний о клиентах при наименьших затратах (Рис, 2009; пересказ).

Ключевое слово здесь — **знания** (validated learning), а не размер продукта. Рис подчёркивает несколько вещей (по тексту статьи):

- вопреки названию, MVP — это не «самый маленький продукт». Если вам просто нужно закрыть очевидную потребность или быстро перепродать продукт, MVP не нужен;
- MVP добавляет работы: из первой итерации нужно извлечь знания, а для этого часто нужны разговоры с клиентами, метрики и аналитика;
- слова «минимальный» и «максимальный» в определении не формула, а повод для суждения: что именно значит MVP в вашем контексте;
- в примерах автора MVP одной из компаний вышел на рынок примерно за полгода, тогда как предыдущему продукту понадобилось почти пять лет. В другом случае две недели ушли на функцию, которая никому не была нужна: простой тест с рекламой показал бы это гораздо раньше.

### MVP и карта историй

С точки зрения карты историй MVP — это первая полоса: Паттон называет хребет карты необходимым для MVP, а минимальная сквозная версия («ходячий скелет») — это то, что нужно собрать первым (см. предыдущую главу). Но MVP отличается тем, что он задаёт **гипотезу**, которую нужно проверить. Если проверять нечего, это просто первый релиз.

Для «Виты» гипотеза MVP может быть такой: «Пациенты записываются онлайн охотнее, чем по телефону». Минимальный набор: найти врача, выбрать время, подтвердить запись. Напоминания, оплата и личный кабинет в него не входят, пока гипотеза не проверена: измеряют долю записей онлайн.

## Разбиение историй: SPIDR

Когда история не помещается в итерацию, её нужно разбить. Мы уже знаем два приёма из главы про INVEST: «ломтями пирога» и spike. Коэн предлагает пять приёмов, названных **SPIDR** (в шутку — «паук без E»), в статье на сайте Mountain Goat Software.

### S — Spike (исследование)

Команда проводит исследование или прототипирование, чтобы получить знания, нужные для разбиения. Пример из статьи: перед добавлением автосубтитров к видео можно изучить готовые решения (строить самим или покупать). Автор отмечает, что spike — не первый инструмент, к которому стоит тянуться.

### P — Paths (пути)

Разбиение по **альтернативным путям** выполнения. Пример из статьи: историю «поделиться видео с друзьями» можно разбить, потому что при нажатии «Поделиться» доступно 14 кнопок соцсетей, ссылка для копирования и запуск с определённого момента — всего 16 путей. Каждый путь — отдельная история.

Для «Виты»: «Пациент записывается на приём» разбивается на пути: через сайт, через мобильное приложение, по телефону оператору.

### I — Interfaces (интерфейсы)

Сначала простая версия интерфейса, потом сложная. Пример из статьи: сначала работа только в Chrome, Safari — в следующей итерации. Другой пример: сначала только URL для обмена, затем простой список соцсетей, затем выбор по логотипам.

### D — Data (данные)

Сначала поддерживается упрощённый или ограниченный набор данных. Пример: сервис принимает 16 форматов файлов, а в первой версии только MP4. Другой пример из статьи: система кадров сначала поддерживает одного руководителя на сотрудника, потом нескольких.

Для «Виты»: сначала запись к терапевтам, затем к узким специалистам; сначала один полис, затем несколько.

### R — Rules (правила)

Временное ослабление правил. Пример из статьи: первая итерация загрузки видео не проверяет запрет на музыку, защищённую авторским правом; фильтр комментариев добавляется через пару итераций.

Для «Виты»: сначала запись без проверки пересечений с другими записями пациента, затем с проверкой. Это допустимо только для пилота или демонстрации, а не для рабочей системы.

## Бэклог DEEP

Чтобы список историй оставался полезным, Роман Пичлер предлагает проверять бэклог по четырём признакам, образующим слово **DEEP** (по тексту статьи):

- **D**etailed appropriately — **подробность по приоритету**: чем выше приоритет, тем подробнее запись;
- **E**stimated — **оценён**: оценки грубые (story points или идеальные дни), единицу выбирает команда; оценивают прежде всего то, что нужно для ближайшей цели;
- **E**mergent — **живой**: пункты появляются из обратной связи, меняются, переприоритизируются и удаляются;
- **P**rioritised — **упорядочен**: верхние пункты делаются первыми; Пичлер советует приоритизировать сначала по риску, затем по соотношению затрат и пользы и по зависимостям.

Страница Пичлера не называет того, кто придумал аббревиатуру DEEP, поэтому авторство термина здесь не утверждается.

## Итоги

- MVP — средство получить проверенные знания, а не просто маленький продукт.
- SPIDR — пять приёмов разбиения: spike, пути, интерфейсы, данные, правила.
- DEEP — проверка бэклога: подробность по приоритету, оценки, живость, упорядоченность.
