**Как пользоваться словарём.** Здесь собраны сокращения и понятия модуля. В главах каждое сокращение расшифровано при первом упоминании, а здесь их можно найти все сразу.

## Сокращения

| Сокращение | Расшифровка | Глава |
|---|---|---|
| API | Application Programming Interface, программный интерфейс | 2 |
| HTTP | HyperText Transfer Protocol, протокол передачи гипертекста | 8 |
| JSON | JavaScript Object Notation, формат записи данных | 8 |
| EDA | Event-Driven Architecture, событийно-ориентированная архитектура | 3 |
| CQRS | Command Query Responsibility Segregation, разделение ответственности на команды и запросы | 4 |
| CRUD | Create, Read, Update, Delete: создание, чтение, изменение, удаление | 4 |
| DDD | Domain-Driven Design, предметно-ориентированное проектирование | 6 |
| REST | Representational State Transfer, передача состояния представления | 7 |
| BFF | Backends for frontends, отдельный шлюз для каждого типа клиента | 2 |

## Понятия

| Термин | Значение | Глава |
|---|---|---|
| Архитектурно значимое требование | требование, которое нельзя «добавить потом» без переделки структуры системы | 1 |
| Атрибут качества | нефункциональная характеристика системы: скорость, надёжность, безопасность и другие | 1 |
| Компромисс | выбор между атрибутами качества, когда улучшение одного ухудшает другой | 1 |
| База на сервис | шаблон: данные сервиса приватны, доступ только через его API | 2 |
| Шлюз API | единая точка входа для клиентов | 2 |
| Размыкатель цепи | прокси, который прекращает вызовы сбойного сервиса на время таймаута | 2 |
| Сага | цепочка локальных транзакций с компенсирующими транзакциями | 2 |
| Хореография, оркестрация | два способа согласовать шаги саги: через события или через оркестратор | 2 |
| Событие | сообщение о том, что уже произошло | 3 |
| Команда | сообщение с просьбой что-то выполнить | 3 |
| Канал | путь, по которому идут сообщения (очередь, тема и т. п.) | 3 |
| Публикация–подписка | канал, где каждый подписчик получает копию сообщения | 3 |
| Оповещение о событии | событие сообщает о факте, получатель при необходимости запрашивает детали | 4 |
| Перенос состояния событием | событие несёт данные, получатель обновляет свою копию | 4 |
| Журнал событий (Event Sourcing) | изменения состояния хранятся как последовательность событий | 4 |
| Исходящие сообщения (Outbox) | событие пишется в таблицу в одной транзакции с данными, отдельный процесс отправляет его | 4 |
| Идемпотентный получатель | получатель, для которого повторная доставка сообщения безвредна | 4 |
| Программная система (C4) | высший уровень абстракции: то, что приносит ценность пользователям | 5 |
| Контейнер (C4) | приложение или хранилище данных, которое должно работать для работы системы; не Docker | 5 |
| Компонент (C4) | группа связанной функциональности за чётким интерфейсом | 5 |
| Единый язык | общий строгий язык разработчиков и экспертов предметной области | 6 |
| Ограниченный контекст | граница, внутри которой модель и термины однозначны | 6 |
| Карта контекстов | схема связей между ограниченными контекстами | 6 |
| Агрегат | кластер объектов с корнем, отвечающим за целостность | 6 |
| Query, mutation, subscription | три вида операций GraphQL: чтение, изменение, получение данных в реальном времени | 8 |
| Схема GraphQL | набор типов сервиса | 8 |
| Канал, сообщение, операция (AsyncAPI) | элементы описания событийного API | 8 |
| `$ref` | ссылка на другой компонент описания OpenAPI | 9 |
| `components` | раздел OpenAPI для повторно используемых описаний | 9 |
| `operationId` | уникальный идентификатор операции в спецификации OpenAPI | 9 |
