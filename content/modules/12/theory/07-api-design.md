**Цель главы.** Вы научитесь переходить от модели предметной области к первому наброску API: ресурсам, операциям и событиям, ещё до написания спецификации.

## Высокоуровневое и детальное проектирование

В модуле 9 вы проектировали API школы по шагам: ресурсы, адреса, методы, ответы, тела запросов. Это детальное проектирование. Здесь на шаг раньше: **высокоуровневое проектирование API** отвечает на вопросы «какие у системы будут интерфейсы, кто их использует, в каком стиле они работают и что через них проходит». Детали (поля, коды ошибок) получаются потом, и ошибки на высоком уровне стоят дороже, потому что от интерфейса зависят все, кто его использует.

## Шесть шагов (рабочая схема курса)

1. **Сценарии и участники.** Кто пользуется интерфейсом: приложение пациента, администратор, другая система. Что он хочет сделать.
2. **Ресурсы из модели предметной области.** Берём агрегаты ограниченного контекста (глава 6): корень агрегата становится ресурсом, внутренние объекты чаще остаются в его теле.
3. **Стиль взаимодействия.** Для каждого сценария решаем: запрос с ответом (REST, то есть Representational State Transfer, передача состояния представления; разобран в модуле 9), гибкая выборка (GraphQL, глава 8) или событие (AsyncAPI, глава 8).
4. **Операции и результаты.** Что можно делать с ресурсом, что получается в ответ, какие бывают ошибки бизнес-правил.
5. **Границы данных.** Что отдаём наружу, а что остаётся внутри контекста.
6. **Соглашения.** Именование, формат ошибок, повторные запросы, версии.

## Шаг 2 на примере «Виты»

Ограниченный контекст «Запись» (глава 6) содержит агрегат «Запись». Корень — запись, внутри услуги и статус.

| Что в модели | Что в API |
|---|---|
| Корень агрегата «Запись» | ресурс `/appointments` (множественное число, как в главах 6–7 модуля 9) |
| Услуги внутри записи | вложены в тело записи, отдельного ресурса нет |
| Слот из контекста «Расписание» | в записи только идентификатор слота; за подробностями идут в API расписания |
| Действие «отменить запись» | операция над ресурсом записи, а не отдельный ресурс-глагол |

## Шаг 3: выбор стиля по сценарию

| Сценарий | Стиль | Почему |
|---|---|---|
| Пациент создаёт запись | запрос и ответ (REST) | нужен немедленный результат: создано или слот занят |
| Мобильному приложению нужен короткий список ближайших записей с врачом и клиникой | гибкая выборка (GraphQL) или специальный запрос шлюза | экономим число обращений на медленной сети |
| Запись создана, нужно оповестить | событие (AsyncAPI) | отправителю не важно, кто и когда обработает |

## Шаги 4–5: операции, ошибки и границы

Для создания записи опишем операцию в виде таблицы; потом из неё получится спецификация.

| Поле | Значение |
|---|---|
| Операция | создать запись |
| Кто вызывает | приложение пациента, администратор |
| Запрос | пациент, слот, услуга |
| Успех | запись создана (код 201), в ответе её идентификатор и статус |
| Бизнес-ошибки | слот уже занят (код 409 Conflict); пациент не найден (404) |
| Что не отдаём | внутренние служебные признаки, данные других пациентов |

Код **409 Conflict** сообщает, что запрос конфликтует с текущим состоянием ресурса. Для слота, который успел занять другой пациент, это подходит лучше, чем общая ошибка запроса. Решение о коде фиксируют в каталоге ошибок (глава 8 модуля 9).

**Граница данных.** Внутренняя модель не равна API. Если в таблице `appointments` хранится поле `internal_risk_score`, это не повод отдавать его в API. Интерфейс — договор с потребителями, и каждое поле в нём потом трудно убрать.

## Шаг 6: соглашения

- **Имена.** Единый язык контекста (глава 6): в API то же слово, что и в разговоре с заказчиком.
- **Единый формат ошибок.** Код, понятное сообщение, поле, к которому относится ошибка. Тогда клиенту не нужно разбирать каждую ошибку по-своему.
- **Повторы.** Метод POST не идемпотентен (модуль 9, глава 6): при обрыве связи клиент может отправить запрос дважды и получить две записи. Для «Виты» нужно решить заранее, как защитить создание записи от повтора, например проверкой «этот пациент уже записан на этот слот».
- **Версии.** В спецификации указывают версию API, а изменения, ломающие потребителей, оформляют как новую версию. Правила изменения версий согласуют с потребителями.

## Чек-лист высокоуровневого проекта

- Для каждого сценария указан стиль взаимодействия.
- Ресурсы выведены из агрегатов, а не из таблиц базы.
- У каждой операции описаны успех и бизнес-ошибки.
- Определено, что остаётся внутри контекста.
- Названия совпадают с единым языком проекта.
- Описано поведение при повторе запроса.

## Проверьте себя

- Чем высокоуровневое проектирование API отличается от детального?
- Как из агрегата получить ресурс? Что делать с объектами внутри агрегата?
- Какой стиль подойдёт для сценария «оповестить о созданной записи» и почему?
- Почему API не должен повторять структуру таблиц базы данных?
- Как защитить операцию создания от повторной отправки?

## Итоги

- Сначала сценарии и участники, потом ресурсы, стиль, операции, границы, соглашения.
- Ресурсы выводятся из агрегатов ограниченных контекстов.
- Стиль выбирают по сценарию: запрос с ответом, выборка по запросу или событие.
- Интерфейс — договор: что отдавать наружу, решают осознанно.
