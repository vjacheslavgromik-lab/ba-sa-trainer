**Цель главы.** Вы узнаете два стиля API, дополняющих запрос-ответ в стиле REST: гибкие запросы на примере GraphQL и описание событий по спецификации AsyncAPI.

## Три стиля рядом

| Стиль | Идея | Где применяют | Чем описывают |
|---|---|---|---|
| Ресурсы по HTTP (HyperText Transfer Protocol, протокол передачи гипертекста) (REST) | клиент вызывает операции над ресурсами | большинство внешних API | OpenAPI (глава 9) |
| Выборка по запросу (query-based) | клиент сам описывает, какие поля ему нужны | мобильные приложения, витрины данных | схема GraphQL |
| События и сообщения | отправитель публикует сообщение, получатели подписаны | интеграции, события предметной области | AsyncAPI |

## GraphQL: выборка по запросу

По материалам graphql.org, GraphQL строится вокруг строгой системы типов и позволяет создавать гибкие API без версий. Основа — **схема**: набор типов сервиса. Запросы проверяются по схеме и выполняются по ней.

**Три вида операций:**

- **query** — чтение данных;
- **mutation** — изменение данных, с побочными эффектами;
- **subscription** — получение данных в реальном времени (отдельной страницы с определением в прочитанных материалах нет).

**Типы.** Документация называет шесть видов именованных типов: объект (Object), скаляр (Scalar), перечисление (Enum), интерфейс (Interface), объединение (Union) и входной объект (Input Object). Встроенные скаляры: Int, Float, String, Boolean, ID. Обязательная точка входа — тип Query, типы Mutation и Subscription добавляются отдельно. Знак `!` после типа означает, что значение не может быть пустым.

**Главное отличие от запросов REST, которое прямо называет документация:** связанные данные можно получить за один запрос вместо нескольких обращений. Форма ответа повторяет форму запроса, а у каждого поля и вложенного объекта могут быть свои аргументы.

**Пример «Виты».** Схема:

```graphql
type Appointment {
  id: ID!
  status: String!
  slotStart: String!
  doctor: Doctor!
  clinic: Clinic!
}

type Doctor {
  id: ID!
  name: String!
  speciality: String!
}

type Clinic {
  id: ID!
  name: String!
}

type Query {
  myAppointments(patientId: ID!, limit: Int): [Appointment!]!
}
```

Запрос мобильного приложения на экран «Мои записи»:

```graphql
query {
  myAppointments(patientId: "P-77", limit: 3) {
    id
    slotStart
    doctor { name }
    clinic { name }
  }
}
```

Приложение получает ровно те поля, которые показывает, одним обращением. С REST то же потребовало бы запроса записей и затем запросов врачей и клиник, либо отдельной специальной операции.

**Что платим.** Из прочитанных страниц цены GraphQL вывести нельзя, поэтому не будем делать вид, что знаем. На практике аналитик обсуждает с архитекторами кэширование, ограничения на сложность запроса и права доступа к полям, а источники для этого читаются отдельно.

## AsyncAPI: описание событий и сообщений

Инициатива AsyncAPI открытая, цель — улучшить состояние событийно-ориентированных архитектур. По аналогии с OpenAPI для REST она создаёт спецификацию для описания асинхронных API. Спецификация началась как адаптация OpenAPI и совместима с его схемами данных.

**Понятия** (по документации):

- **Канал (channel)** — механизм, созданный сервером, чтобы организовать и передавать сообщения. Зависит от протокола: тема, очередь, ключ маршрутизации, путь.
- **Сообщение (message)** — средство передачи информации от отправителя получателю через каналы; полезная нагрузка сериализуется (JSON, то есть JavaScript Object Notation, или другой формат, в том числе бинарный), метаданные называются заголовками.
- **Операция (operation)** — действие приложения над каналом: в примере документации поле `action` принимает значение `receive` (получает).

**Главное отличие от OpenAPI** по странице для тех, кто переходит с OpenAPI: у AsyncAPI несколько протоколов вместо одного HTTP, а начиная с версии 3.0 операции вынесены из каналов в отдельный раздел.

**Структура документа** (из примеров документации): `asyncapi` (версия), `info` (название и версия), `channels`, `operations`. В примерах документации указана версия 3.1.0.

**Пример «Виты»:** канал событий о записях.

```yaml
asyncapi: 3.1.0
info:
  title: Вита. События записи
  version: 0.1.0
channels:
  appointmentEvents:
    address: vita.appointments
    messages:
      appointmentBooked:
        payload:
          type: object
          required: [eventId, appointmentId, patientId, slotStart]
          properties:
            eventId:
              type: string
            appointmentId:
              type: string
            patientId:
              type: string
            slotStart:
              type: string
              format: date-time
operations:
  publishAppointmentBooked:
    action: send
    channel:
      $ref: '#/channels/appointmentEvents'
  receiveAppointmentBooked:
    action: receive
    channel:
      $ref: '#/channels/appointmentEvents'
```

Документ отвечает на вопросы подписчика: на какой канал подписаться, что за сообщение придёт и какие в нём поля. Значения `send` и `receive` в этом примере показывают сторону приложения. Значение `send` в учебном примере выбрано по аналогии с `receive` из документации. Перед использованием в проекте сверьте пример с актуальной спецификацией AsyncAPI.

## Как выбрать

| Вопрос | Ответ |
|---|---|
| Клиенту нужно сразу выполнить действие и узнать результат | запрос и ответ (REST) |
| Клиентам нужны разные срезы связанных данных | выборка по запросу (GraphQL) |
| Нужно оповестить многих о факте | событие (AsyncAPI) |

Стили сочетаются: у «Виты» мобильное приложение может работать по GraphQL, а между сервисами идут события.

## Итоги

- GraphQL: схема типов, операции query, mutation, subscription, клиент выбирает поля.
- AsyncAPI описывает каналы, сообщения и операции для событийных систем.
- AsyncAPI по структуре напоминает OpenAPI, но поддерживает много протоколов.
- Стили не конкурируют, а дополняют друг друга.
