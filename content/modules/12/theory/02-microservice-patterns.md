**Цель главы.** Вы узнаете четыре шаблона, которые чаще всего решают проблемы микросервисов: база на сервис, шлюз API (Application Programming Interface, программный интерфейс), размыкатель цепи и сага, и поймёте, какую цену платят за каждый.

## Зачем нужны шаблоны

В модуле 8 вы разобрали, чем микросервисы отличаются от монолита и какую цену за них платят. Когда система разделена на сервисы, появляются проблемы, которых не было внутри одной программы: где хранить данные, как клиенту обращаться ко многим сервисам, что делать при отказе соседа, как довести до конца операцию, которая затрагивает несколько сервисов. Для каждой есть известное решение, которому дали имя, то есть **шаблон**. Автор каталога, Крис Ричардсон, описывает каждый шаблон одинаково: проблема, решение, плюсы и минусы. Так разберём и мы.

## База на сервис (Database per service)

**Проблема.** Сервисы должны быть слабо связаны, но часть транзакций и запросов затрагивает данные нескольких сервисов.

**Решение.** Данные сервиса приватны: доступ к ним только через API этого сервиса, а транзакции затрагивают только его базу. Изолировать можно по-разному: приватные таблицы, отдельная схема или отдельный сервер базы данных.

**Плюсы.** Слабая связанность; для сервиса можно выбрать подходящий тип хранилища.

**Минусы.** Распределённые транзакции лучше избегать; сложные запросы с объединением данных из нескольких баз трудны; разных баз становится больше, и ими надо управлять. Для кросс-сервисных задач автор предлагает сагу (для операций) и отдельную модель для чтения (для запросов, глава 4).

**«Вита».** Сервис расписания владеет слотами врачей, сервис записей владеет записями. Сервис записей не читает таблицы расписания напрямую, он обращается к сервису расписания через его API.

## Шлюз API (API Gateway)

**Проблема.** Клиентам нужны данные от нескольких сервисов, разным клиентам нужны разные данные (веб, мобильное приложение, сторонние), мобильная сеть медленнее, а адреса сервисов меняются.

**Решение.** Единая точка входа для клиентов. Один запрос она может передать в один сервис, другой разослать нескольким. Вариант — **Backends for frontends (BFF)**: отдельный шлюз на каждый тип клиента.

**Плюсы.** Клиент изолирован от разбиения на сервисы и их адресов, обращений к серверам меньше, API можно подогнать под клиента.

**Минусы.** Ещё один компонент для разработки и эксплуатации; лишний сетевой переход добавляет задержку.

**«Вита».** Веб-приложение и мобильное обращаются к шлюзу, а шлюз знает, какой запрос уйдёт в расписание, а какой в записи.

## Размыкатель цепи (Circuit Breaker)

**Проблема.** Сбой одного сервиса может каскадом передаться другим: синхронные вызовы занимают потоки, и ресурсы вызывающего сервиса заканчиваются.

**Решение.** Вызов идёт через прокси, похожий на автоматический выключатель. Когда число подряд идущих ошибок превышает порог, прокси «размыкается»: вызовы на время таймаута завершаются сразу, без обращения к сбойному сервису. Потом пропускается ограниченное число пробных запросов; если они успешны, цепь «замыкается», иначе таймаут начинается заново.

**Плюсы.** Сервис переживает сбои зависимостей.

**Минусы.** Трудно подобрать таймауты: слишком короткие дают ложные срабатывания, слишком длинные дают лишнее ожидание.

**«Вита».** Если SMS-шлюз недоступен, запись всё равно создаётся, а уведомление отправится позже. Размыкатель не даёт сервису уведомлений «зависать» на каждом вызове.

## Сага (Saga)

**Проблема.** Бизнес-операция затрагивает несколько сервисов, а обычную транзакцию на несколько баз сделать нельзя (или нежелательно).

**Решение.** Операция разбивается на последовательность **локальных транзакций**, по одной в каждом сервисе. Если шаг нарушает бизнес-правило, уже выполненные шаги отменяются **компенсирующими транзакциями**. Автоматического отката нет: компенсации проектирует разработчик, и аналитик должен описать их в требованиях.

Два способа согласовать шаги:

- **Хореография.** Каждая локальная транзакция публикует событие, на которое подписан следующий участник. Единого «режиссёра» нет.
- **Оркестрация.** Особый объект, **оркестратор**, говорит участникам, какую локальную транзакцию выполнить, и получает ответы.

Пример автора: создание заказа и резервирование кредитного лимита клиента. При хореографии сервис заказов создаёт заказ в состоянии PENDING (ожидает) и публикует событие, сервис клиентов пытается зарезервировать лимит и публикует результат, сервис заказов подтверждает или отклоняет заказ. При оркестрации оркестратор создаёт заказ, отправляет команду зарезервировать кредит и по ответу подтверждает или отклоняет.

**Плюсы.** Согласованность данных без распределённых транзакций.

**Минусы.** Нет автоматического отката; нет изоляции (пока сага идёт, другие операции видят промежуточные данные); публикация сообщения и запись в базу должны быть атомарны (решение — «исходящие сообщения», глава 4); клиенту надо как-то узнать исход асинхронного процесса.

**«Вита».** Запись на приём затрагивает расписание, платёж и уведомления:

| Шаг | Сервис | Если дальше сбой, компенсация |
|---|---|---|
| 1. Удержать слот | расписание | освободить слот |
| 2. Создать запись в статусе «ожидает оплаты» | записи | перевести запись в «отменена» |
| 3. Списать предоплату | платежи | вернуть деньги |
| 4. Подтвердить запись и отправить уведомление | записи, уведомления | отправить уведомление об отмене |

## Как аналитик использует шаблоны

Шаблон — это не требование, а ответ на проблему. Аналитик отвечает за проблему: какие данные не должны смешиваться, какие операции затрагивают несколько частей системы, какие сбои допустимы. Сопоставьте: «операция затрагивает три сервиса» ведёт к саге, а значит, в требованиях нужны сценарий отмены и ответ «что видит пациент, пока сага идёт».

## Проверьте себя

- Почему сервису записей нельзя читать таблицы расписания напрямую?
- Какую проблему решает шлюз API и какой ценой?
- Что происходит с вызовами, когда размыкатель цепи разомкнут?
- Чем хореография саги отличается от оркестрации?
- Какие компенсирующие транзакции нужны, если оплата не прошла после удержания слота?

## Итоги

- Шаблон называет проблему, решение, плюсы и минусы.
- База на сервис даёт независимость, но запросы по нескольким базам становятся сложными.
- Шлюз API — единая точка входа ценой лишнего компонента и задержки.
- Размыкатель цепи останавливает каскад сбоев.
- Сага заменяет распределённую транзакцию цепочкой локальных и компенсаций; компенсации придумывают заранее.
