**Цель главы.** Вы получите памятку: какой метод курса применить на каждом этапе, какие ошибки встречаются чаще всего и по какому общему чек-листу проверяет строгий ревьюер.

## Куда смотреть на каждом этапе

| Этап | Где метод | Частые ошибки |
|---|---|---|
| 1. Выявление требований | модуль 2: образ и границы, классы пользователей, трассируемость; модуль 7: истории, критерии приёмки, INVEST | цель без числа; требования-решения вместо требований-задач; нет критериев приёмки; не названы ограничения и допущения |
| 2. Процессы | модуль 5: BPMN, диаграмма состояний | поток сообщений внутри одной дорожки; состояния, в которые нельзя попасть; нет обработки исключений (клиент не пришёл, снаряжение вернули поздно) |
| 3. Данные | модуль 3: SQL; модуль 4: ER, ключи, кратность, нормализация, словарь данных | связь «многие ко многим» без промежуточной сущности; нет ключей; нет атрибутов связи; названия не совпадают с процессами |
| 4. Прототип | модуль 6: персоны, карта сайта, требования к элементам | экран без ошибок и пустых состояний; элемент описан без типа и правил |
| 5. Интеграции и API | модуль 9: REST, коды ответов, спецификация; модуль 12: события, OpenAPI | нет бизнес-ошибок (занято, не найдено); операции не совпадают с процессом; схемы с полями, которых нет в данных |
| 6. ПМИ и презентация | модуль 11: ПМИ, приёмка; модуль 10: тест-кейсы | требование без способа проверки; критерий без числа; презентация о технологиях вместо результата для заказчика |

## Общий чек-лист строгого ревьюера

Эти вопросы ревьюер задаёт к каждому этапу:

1. **Измеримо?** У целей и нефункциональных требований есть число, условия и допуск.
2. **Проверяемо?** По каждому требованию можно составить тест.
3. **Единый язык?** Одни и те же понятия называются одинаково во всех этапах: «аренда», «позиция аренды», «единица снаряжения».
4. **Согласовано?** Статусы в процессе, в данных и в API совпадают; правила не противоречат друг другу.
5. **Выявлены исключения?** Описано, что происходит, если клиент не пришёл, снаряжение занято, вернули с повреждением, оплата не прошла.
6. **Названы допущения и ограничения?** Видно, что вы выяснили у заказчика, а что предположили сами.
7. **Прослеживается цель?** От каждого результата можно дойти до бизнес-цели.
8. **Есть риски?** Названы главные риски и что с ними делать.
9. **Понятно заказчику?** Документ читается без пояснений и без жаргона, где он не нужен.
10. **Нет лишнего?** Нет функций «на вырост», которых никто не просил и не оплачивал.

## Форма сдачи

Ответ на каждом этапе пишите текстом в окне «Ваш ответ». Таблицы можно записывать в виде строк с разделителем `|`. ER-диаграмму записывайте в формате Mermaid `erDiagram` (как в модуле 4), спецификацию API — на YAML (как в модуле 12), диаграммы процессов и состояний — текстом: шаги, переходы со стрелками `->`. Эталоны оформлены так же, чтобы вы могли сравнивать.

## Как сверяться с эталоном

- Сначала выполните этап сами, потом откройте эталон.
- Не копируйте формулировки эталона: цель в том, чтобы вы сами нашли решения.
- Сверяйте **решения и согласованность**: названия, статусы, правила, исключения.
- Если вы нашли важное, чего нет в эталоне, это хорошо: эталон — один из возможных ответов.

## Итоги

- Для каждого этапа есть метод в курсе и типичные ошибки.
- Ревьюер проверяет измеримость, проверяемость, единый язык, согласованность, исключения, допущения, цель, риски, понятность и отсутствие лишнего.
- Формы сдачи те же, что в модулях 4 и 12.
- Эталон — один из возможных ответов; сверяйте решения и согласованность, а не слова.
